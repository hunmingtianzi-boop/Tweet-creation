# 组织型公众号工作流使用说明

这套工作流用于“换一个组织或公众号，仍能继续生成属于它的文章、视觉素材和微信交付文件”。

## 使用归属

使用本仓库工作流制作的公开推文，在所有正文和自定义 footer 之后必须保留一次可见文本：`感谢拓浙 AI 生态提供本篇内容生产工作流支持。`。它是仓库级使用归属，不是组织品牌文案；Ardot 中保留末位原生可编辑文本，编译、handoff v5 和草稿回读均会校验。

## 零、启动环境自检

任何组织材料读取、Ardot 创建或公众号操作之前，先按[运行环境启动自检](runtime-preflight.md)生成当前会话 profile。profile 必须绑定项目根 `org-wechat-studio` 与仓库内 publisher Skill 的实际 SHA、当前 provider/session、runtime callable 和无凭据 Ardot/微信链接。只运行 `--binding-only`，确认 URL 与工具路由合同安全后，才允许把链接传给 MCP/Browser；实际 probe 必须是当前宿主轨迹里的真实工具调用，不写回 profile 冒充证据。

启动默认要求：

- 每次工作流/组织迁移到新 harness、LLM、机器、adapter、provider route，或 trusted bundle 改变时，先跑 `--phase migration --binding-only`。该阶段只绑定两类生图与验图，并在读材料前强制完成一次 `neutral-rgba-route-probe-v1`；
- `authoring/full` 同时绑定 `image.generate.opaque`、RGBA 生产路由与 `image.inspect`。Codex Desktop 默认的 RGBA 路由是 `chatgpt-web-image-route` + `codex-with-chatgpt` + 内置 Browser，再经 `scripts/prepare_micro_cutout.py`；本地 `image_gen__imagegen` 只可承担不透明源图，不得冒充 Alpha 生产器；
- `ardot.read` + `ardot.write` + `ardot.export`，或通过实际登录探测的 UI 路线；
- `wechat.draft`，或能读取当前目标账号的 Browser/Computer Use 路线；
- `host.receipt.attest` 是 `portable-signed-audit` 的可选增强：能力存在时还需 root-owned、非 symlink、组/其他用户不可写的 Ed25519 公钥信任库。当前 Codex Desktop adapter 标记该能力 `unavailable`，因此本机 `delivery/full` 选择 `current-session-draft`：仍可创建并回读验证草稿，但必须标记 `portable_audit_verified: false`，不可声称可携带签名审计；
- `secret.resolve`，并能无泄漏地确认 `PROVENANCE_WATERMARK_KEY` 引用存在且格式合格，以及 `PROVENANCE_WATERMARK_PRIVATE_ROOT` 位于 Git 外、非 symlink 且可写；
- Python、Pillow、cryptography（Ed25519 验签）、工作区读写、全部本地引用与项目 Skill SHA 一致。

缺少某项时先修复连接、登录或 secret，再重新运行。不要把 token、Cookie、AppSecret、密钥、ChatGPT 对话 URL/配对码或当前微信带 token 的编辑 URL写入 profile。`migration/authoring/full` 在读材料前先执行 host setup actions：加载两个 ChatGPT 技能，运行 C2C update/sandbox/session 检查，保持一个可见的内置 Browser 标签；若显示登录/2FA/同意页，只请用户完成该步，然后在同一 session 重探。`migration` 还必须按报告的精确 prompt/路径完成一次 native-alpha-first ChatGPT/provider request、生成、original download、raw PNG 事实、secure RGBA 处理与 exact derivative 透明/浅/深三底验收。nonce/digest 只写宿主 canonical request metadata 并由其 SHA 关联同一事件链，不写入生图 prompt。探针只放 `output/runtime/migration-probes/<nonce>/`，不进入 assets.json、Ardot、水印或后续风格 prompt。ChatGPT-web migration 遵守 C2C 单对话规则，不开临时验证 chat；探针只允许无对象、无品牌、单一中灰的非语义校准轮廓，正式 prompt 明确排除该轮廓与灰度测试处理。`authoring/full` 报告中的 `enforce-migration-rgba-route-gate` 是宿主工作流硬门禁，本地 CLI 不能认证旧 trace。进入下面步骤的条件是：binding report 的 `ok` 和 `binding_ready` 同时为 true，且宿主轨迹中所选路线的真实探针全部成功。本地报告的 `phase_ready` 保持 false 是防假绿设计，不是让模型手动改成 true。

新组织没有 Ardot file/root 时不要伪造链接：迁移自测通过后，再用 `--phase bootstrap --binding-only` 检查 `ardot.create`，宿主轨迹确认 create-design/page callable 后只创建空白设计，随即用新 file/root 重跑目标阶段（默认 `full`，明确只做 Ardot 时为 `authoring`）。`bootstrap` 不要求生图、ChatGPT、验图、水印 secret、微信账号或登录。

## 一、已有组织包时

查看可用组织：

```bash
python3 scripts/orgs.py list
```

验证组织包：

```bash
python3 scripts/orgs.py validate organizations/<organization-id>
```

查看某类文章适合的视觉路线与组件：

```bash
python3 scripts/orgs.py recommend organizations/<organization-id> recruitment
```

搜索可复用素材：

```bash
python3 scripts/orgs.py search organizations/<organization-id> "招新 校园"
```

## 二、迁移到新公众号

不读取任何组织材料，先准备最小 migration profile：它不含 Ardot/微信链接，只绑定 opaque、RGBA、inspect；RGBA 项声明 `migration_probe_contract: neutral-rgba-route-probe-v1` 和与 adapter 一致的真实 `generation_route_id`。然后运行：

```bash
python3 -I -S scripts/secure_runner.py scripts/runtime_preflight.py \
  output/runtime/migration-profile.json \
  --phase migration --binding-only \
  --output output/runtime/migration-binding-report-UNIQUE.json
```

立即执行报告的 `host_setup_actions`。宿主轨迹未完成 `run-migration-rgba-route-probe` 前，下面的 `orgs.py init` 不得运行。ChatGPT-web 路线保持同一 C2C-managed conversation，不新开临时验证 chat；中性 probe 仅为非语义灰度校准，不是组织资产，不得作为视觉参考或正式资产证据。

首先为该公众号建立独立组织包：

```bash
python3 scripts/orgs.py init new-account-id \
  --name "新组织或公众号名称" \
  --root organizations
```

将生成：

```text
organizations/new-account-id/
├── organization.json
├── sources.json
├── components.json
├── assets.json
├── ardot.json
└── assets/
    ├── official/
    ├── photos/
    ├── generated/
    └── derived/
```

然后完成组织调研：

1. 收集本轮明确允许的官网说明、原始文案、Logo、活动照片与品牌规范。默认不要打开旧推文布局、旧截图/PDF、旧 Ardot 或其他组织 pack；获准的历史文字只能用于 voice/fact，不能用于视觉校准。只有用户明确要求学习某个风格时，才进入 [style-options.md](style-options.md) 的 `explicit-style-grammar` 分支。
2. 在 `sources.json` 中记录来源和可核验事实。
3. 在 `organization.json` 中确认受众、内容支柱、语气、视觉色彩、视觉母题和文章类型。
4. 默认在 `organization.provenance` 填写 `visual_reference_policy: source-zero`、本轮 `visual_input_source_ids`、四类旧视觉排除项和 `isolation_reviewed_at`。若用户明确选了 style preset，则改用 `explicit-style-grammar` 的来源、scope、review time 与六项 non-copy 契约；后续组织把 preset JSON 登记为来源，不重新打开最初参考。
5. 为每个文章类型提出 2–3 条视觉路线，先在全新 Ardot 页面做 Hero、章节、照片编排、微型插图和信息密度小样，不直接做全文。已审核 preset 只能作为其中一个 route 级选项；未带 `style_grammar` 的 sibling routes 仍是 source-zero。Hero/章节同时对比可编辑表现型标题字，至少批准两个 construction recipe；每个 recipe 至少两种非字体手法与两个可编辑图层，只换字体不算艺术字。AI 底图必须先做一个母版与 1–3 个同系列变体，整个 family 只能选一种 `light`/`dark` surface mode，并登记 family/variant、归一化 copy-safe zone、正文颜色、最低 4.5 对比度和复制区最大 0.10 亮度标准差，不能逐章随机生成。组织包默认启用 `generated_image_watermark.mode: required`；密钥来自仓库外的 `PROVENANCE_WATERMARK_KEY`，必须是以 `hex:` 或 `base64:` 表示的至少 32 个随机字节，不能写进组织包。

```bash
python3 scripts/build_visual_directions.py \
  organizations/new-account-id recruitment \
  --output output/new-account-id/visual-directions.json
```

仓库当前内置的可选 preset 可在 `style-presets/` 查看。`prismatic-paper-editorial` / 绚烂纸本是暖纸、水彩洗染、干刷与颗粒的连续阅读面语法，不是默认配色模板。选择时只把 preset 的 `grammar` 写入被选 route，组织色、字体、照片与组件仍由本组织材料重新校准。`orgs.py validate` 会把 route SHA 与仓库 canonical preset 对照；修改 token 后重新签一个自有 SHA 也不能通过。

6. 用户批准小样后，把 route、background family、typography recipes 与 Ardot 文件/页面/节点回写到 `organization.visual.calibration`。先登记最终 master/companion PNG，再运行下面的验证；它会直接分析像素，阻断明暗跳变、大块黑白、复制区杂乱和文字对比不足。只有通过后才创建文章 root。组织事实与视觉同时确认后，才将状态改为 `confirmed`。`provisional` 组织会被阻断在全文之前。

```bash
python3 scripts/orgs.py validate organizations/new-account-id
```

如果同一组织有多个公众号：

- 语气、受众、视觉与栏目完全一致时，可共用组织包，只更换发布连接。
- 如果是子品牌、校园分会、招新号或不同受众频道，建议建立独立组织包，避免品牌混同。

## 三、为新公众号生成对应资产

先生成资产计划：

```bash
python3 scripts/orgs.py asset-plan \
  organizations/new-account-id recruitment \
  --output output/new-account-id/recruitment-asset-plan.json
```

资产计划会根据该组织的：

- 品牌色与视觉母题；
- 文章类型；
- 当前视觉路线；
- 已有素材库；
- 真实照片与生成图像的边界；

输出每个资产位的状态、建议尺寸、保存目录和生图提示蓝图。

系统可以生成：

- 封面或开场背景；
- 章节主视觉；
- 透明背景点缀插画；
- 流程、系统与技术解释图；
- 照片裁切、压缩和派生版本；
- 与组织视觉路线一致的组件背景资产。

不会生成：

- Logo 或组织标志；
- 报名码、群二维码或公众号二维码；
- 冒充真实人物、活动现场或项目成果的图片；
- 带有生成中文、虚假数据或合作伙伴标志的图像。

将用户提供或已审核的文件放入对应目录。对于不透明的 `generated-illustrative` 底图或纯生成 raster 封面，先保留母版并生成带来源水印的 final derivative；公开报告留在 pack 内，raw watermark ID 的私密记录必须留在 pack 和 Git 之外。先创建私密目录并设定 `PROVENANCE_WATERMARK_PRIVATE_ROOT`；`--private-record` 必须位于该目录下：

```bash
python3 -I -S scripts/secure_runner.py scripts/provenance_watermark.py embed \
  organizations/new-account-id/assets/generated/recruitment-hero-raw.png \
  organizations/new-account-id/assets/derived/recruitment-hero-final.png \
  --key-epoch 1 \
  --report organizations/new-account-id/assets/derived/recruitment-hero-watermark.json \
  --private-record /secure/private-registry/recruitment-hero.json
```

只有报告达到 `local_verified`、`PSNR >= 42 dB` 且完整画面通过 `390px-if-larger → JPEG Q75` 模拟才注册 final 文件：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id visual.recruitment-hero \
  --kind background \
  --title "Recruitment hero background" \
  --location assets/derived/recruitment-hero-final.png \
  --watermark-source assets/generated/recruitment-hero-raw.png \
  --watermark-report assets/derived/recruitment-hero-watermark.json \
  --origin generated-illustrative \
  --style campus-editorial \
  --use recruitment \
  --visual-role illustrative-atmosphere \
  --background-family-id current-family-v1 \
  --background-variant master
```

登记时会用外部密钥重新检测当前像素、独立重跑传输模拟、回算母版/final/公开报告 SHA 与 PSNR，并拒绝源文件覆盖、伪造报告、未知字段、低于视觉门槛的结果或 pack 外路径。成品、公开报告和私密记录都不覆盖已存在路径。真实照片、用户/官方图片、Logo、二维码、透明 `article-micro`、SVG/SMIL 与 QA 截图不修改。V1 不承诺裁切、加边、旋转或透视变换后的截图检出；完整合同见 [provenance-watermark.md](provenance-watermark.md)。

日常查水印用 `detect`（密钥仍由外部 secret manager 注入）：

```bash
audit_dir="$(mktemp -d)"
python3 -I -S scripts/secure_runner.py scripts/provenance_watermark.py detect \
  "/absolute/path/recruitment-hero-final.png" \
  --report "$audit_dir/local-detect.json"
```

退出码 `0` 且报告同时出现 `status: payload_authenticated` / `authenticated: true` 才是通过。本地和微信托管图都要核对 `payload_fingerprint`、`key_epoch`、`version`、`purpose`、`algorithm`；本地图还要求 `input_sha256` 对齐 embed 报告 `post_sha256`。微信端需先下载保存草稿实际返回的 `mmbiz.qpic.cn` 完整图，再运行同一命令；不用截图、裁切图或转码图。退出码 `1` 仅表示 `not_detected`，`2` 表示密钥/输入/路径/格式错误。详见 [provenance-watermark.md](provenance-watermark.md#detection-commands)。

companion 使用相同 family ID，并改为 `--background-variant companion`；在 `organization.visual.calibration.background_family` 同时登记 master、1–3 个 companion，以及：

```json
{
  "surface_mode": "dark",
  "copy_safe_zone": {"x": 0.12, "y": 0.16, "width": 0.76, "height": 0.58},
  "body_text_color": "#FFFFFF",
  "minimum_contrast_ratio": 4.5,
  "maximum_copy_safe_stddev": 0.10
}
```

登记完全部底图后必须再次运行 `python3 scripts/orgs.py validate organizations/new-account-id`。不允许用一张浅色、一张深色拼成 family，也不能在验证失败时进入全文排版。

Logo 或二维码的注册示例：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id brand.logo \
  --kind logo \
  --title "Canonical logo" \
  --location assets/official/logo.png \
  --origin official \
  --style canonical \
  --use all
```

## 四、在 Ardot 生成可编辑文章

根据 `references/article-schema.md` 创建 `article.json`。先写 4–10 个叙事章节，确定每章命题、构图、视觉意图与 block 覆盖：

```bash
python3 scripts/build_storyboard.py article.json \
  --output output/new-account-id/article-slug/storyboard-plan.json
```

分镜批准后先写 `article.interaction_plan`。常规文章使用 `authoring_mode: dynamic-default`，默认 2–3 个 semantic modules：2 个必须分布在实际 early + middle chapters，3 个再增加 late。每个 module 绑定该章 `source_block_indices` 和一个具体读者任务；四个部门分别点击仍只算 1 个 module，但四个 transport instances 要分别登记原文、唯一 fallback key 与 `sha256:<64 hex>`。这套门槛与下面的四类微型视觉套件相互独立，不能用微插图、艺术字或装饰动画凑数。字段与静态例外见 `references/interaction-composition.md`。

只有 `ready_for_visual_kit: true` 才生成文章专属小组件/小插图计划：

```bash
python3 scripts/build_visual_kit.py article.json \
  --org organizations/new-account-id \
  --output output/new-account-id/article-slug/visual-kit-plan.json
```

先按计划生成四枚不同的微型视觉资产。每枚图必须写明 `storyboard_chapter`、正文原句 `source_text`、`concrete_subject`、`action`、`composition_role` 和 `placement`。不再把整篇正文粗暴塞进四个通用生图提示词。

Codex Desktop 必须先加载仓库内 `chatgpt-web-image-route` 和已安装的 `codex-with-chatgpt`。它只使用内置 Browser 操作 ChatGPT，不使用 Computer Use 或外部 Chrome。首轮直接要求 ChatGPT 生成具有真实透明像素的 provider-original PNG，通过页面真实下载动作保存到 `assets/generated/`；截图、预览 Canvas、剪贴板或复制 URL 都不算原图。C2C doctor 成功也只证明连接，不证明生图或 RGBA。

每张原图先生成 create-once 的派生图和报告：

```bash
python3 -I -S scripts/secure_runner.py scripts/prepare_micro_cutout.py \
  organizations/new-account-id/assets/generated/article-object-raw.png \
  organizations/new-account-id/assets/derived/article-object-cutout.png \
  --role floating-spot \
  --article-id ARTICLE_ID \
  --asset-slot-id kit.floating-spot \
  --prompt-sha256 sha256:PROMPT_SHA \
  --generation-route chatgpt-web-image-route-v1 \
  --require-native-alpha \
  --report organizations/new-account-id/assets/derived/article-object-cutout.json
```

首轮的 `--require-native-alpha` 只允许处理器规范化真 Alpha，不允许它推断或移除背景；RGB、全不透明 RGBA、烘焙棋盘格、low-Alpha 色雾都会失败。仅当该下载原图未通过 Alpha/像素门禁时，才使用计划中的 `fallback_prompt` 生成一次均匀、边界连通的受控 key 背景原图，并把参数改成 `--key-color '#KEYHEX'`。背景不均、主体碰边、透明材质无法分离、halo/碎片/底板残留时停止该槽位，不得继续换 key、降低阈值或对任意照片强制抠图。然后逐张运行真实 Alpha、尺寸与角色宽高比检查：

```bash
python3 -I -S scripts/secure_runner.py scripts/inspect_asset.py \
  organizations/new-account-id/assets/derived/article-object-cutout.png \
  --role floating-spot
```

先把登记 ID 写入 `article.visual_kit.assets`；此时若尚未有 Ardot component node，计划仍会保持 `ready_for_layout: false`。资产注册示例：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id spot.article-object \
  --kind illustration \
  --title "Article object spot" \
  --location assets/derived/article-object-cutout.png \
  --origin derived \
  --cutout-report assets/derived/article-object-cutout.json \
  --style article-specific \
  --use recruitment \
  --role floating-spot \
  --generated-for ARTICLE_ID \
  --visual-role article-micro
```

四类角色不能共用图片；四枚派生图都必须在资产登记中明确绑定当前 `article_id`、原图/prompt/路由/处理器/配置/报告 SHA。旧的通用装饰图、raw 下载图或仅改为 RGBA mode 的伪透明图不能解锁排版。验图后先在 Ardot 建四个原生 Ornament 组件，再把每个组件的 `file_url`、`node_id`、exact `name` 写回 `article.visual_kit.assets`。此后才把 status 设为 `approved` 并重跑计划。

然后为本篇文章选定 2–4 个 Hero/章节/观点/关键短语/CTA 表现型字体时刻。每个时刻必须引用正文原句和批准的 `recipe_id`，至少实现两种非字体构造手法，并在 `construction` 中写回独立的 Ardot 文本/矢量 node IDs；主文本的 `file_url/node_id/style_id/name` 也必须完整。只换字体会直接失败。完整字段见 `references/expressive-typography.md`。

```bash
python3 scripts/build_ardot_manifest.py article.json \
  --org organizations/new-account-id \
  --output output/new-account-id/article-slug/ardot-manifest.json
```

清单会包含：

- 目标 Ardot 文件、页面、变量集和组织模式；
- 本篇采用的视觉路线与组件变体；
- 每个区块的真实 Ardot 组件名和覆盖内容；
- 需要上传的组织资产及本地路径；
- 视觉 QA 阻断项与微信投递边界。
- 每个区块的开放式构图模式、微型视觉角色与方框比例限制。

如果 `ardot.json` 仍是 `not-linked`，先在 Ardot 中建立或选择组件系统，再填写：

- `design_file.url` 与 `file_id`；
- `variable_mode`；
- `page_names`；
- `component_aliases`。

随后按清单在 Ardot 中：

1. 先把四类小插图做成无默认底色/描边/圆角的原生 Ornament 组件，并确认表现型字体仍是可编辑文本节点。
2. 应用该组织的变量模式。
3. 获取或创建 Hero、章节、观点、步骤/流程、案例和 CTA 组件变体。
4. 建立 390 px 文章根 Frame；所有区块默认开放、无外框。
5. 为每个 interaction module 建一个原生 group component，保留 `closed`、`open`、`fallback` 三态。三态 node、390 px 截图、文件哈希、当前 revision 和组内 instance/hash 覆盖列表全部写回 `interaction_plan`。
6. 用插图切入文字边缘、章节转场、连续路径和 CTA 落点，不能用方框替代视觉节奏。单个微图片层不超过 72% 行宽、整个实例不超过 82%；含字实例不加文字框/底板，主短句至少 22 px 且为局部正文的 1.35 倍。
7. 按叙事章节装配，不按“一个 block = 一个带外框组件”机械堆叠，也不把动态模块相邻堆成组件墙。
8. 从同一 article root 分别导出 Hero、章节、证据、复杂区块和 CTA 五个不同 Ardot 节点的本地 390 px PNG，记录 node、chapter、SHA-256、实际宽高与 capture 时间到 v3 `visual-review.json`。
9. 从同一根导出 `ardot-article-instance-inventory`，列出四类 visual-kit definitions 的全部实际 instance；再为每个 instance 导出 `ardot-node-properties` JSON，包含 instance/image/text/closed-shape bounds、font size、fill/stroke 和 node IDs。逐文件记录 SHA-256，并把 placement 绑定到对应截图 SHA。不要手填宽度比例、偏移或“无框”。
10. 逐项检查主体相关性、风格一致、装饰裁切、尺度变化、照片/插图和谐、泛 AI 装饰、无意义标签、编辑节奏、手机可读性、开放构图、信息密度、底图家族一致性、表现型字体、无烘焙字图、无文字框、无全宽微图、错落构图和微组件字号层级。
11. 为五个截图节点记录与截图哈希绑定的密度样本。默认 `compact-editorial`：正文 15–17 px、行高 1.45–1.62、中文字距 -0.2–0 px、段距 8–14 px、章内主间隔 24–40 px、普通正文区内容占用率 68%–90%、最大无意空洞不超过 20%。
12. 视觉确认后将 Ardot 保留为唯一可编辑源。

详细规则见 `references/ardot-workflow.md`。

## 五、生成微信投递文件

先验证独立截图验收文件：

```bash
python3 scripts/build_visual_review.py visual-review.json --article article.json
```

把路径写入 `article.visual_review_file`。只有验收通过后，才从当前 Ardot root 冻结 handoff v5 与 `ardot-current-root-layer-export-v1`。编译前再通过当前 Ardot 宿主读取同一精确 file/root，保存到另一份 `qa/live-current-root.json`；不得复制冻结文件充当 live reread。

无 signer 时使用 `current-session-draft`：

```bash
python3 -I -S scripts/secure_runner.py scripts/validate_transport_fidelity.py handoff.json \
  --intended-html output/new-account-id/article-slug/wechat-candidate.html \
  --live-root-export qa/live-current-root.json \
  --require-live-root --session-draft
python3 -I -S scripts/secure_runner.py scripts/compile_wechat.py \
  --transport-fidelity handoff.json \
  --live-root-export qa/live-current-root.json \
  --session-draft \
  --output output/new-account-id/article-slug \
  --check
```

该命令产生 `wechat-candidate.html` 和 `candidate-report.json`。只有当前宿主工具轨迹同时显示真实 Ardot reread 和后续微信操作时，宿主才能把精确绑定的 candidate 作为本次可逆草稿写入的动作输入。未签名报告只证明结构对应，必须为 `candidate_valid: true`、`draft_write_eligible: false`、`portable_audit_verified: false`、`delivery_eligible: false`，不得把宿主动作权序列化为本地 artifact 授权。

有 `host.receipt.attest` 并需要可携带审计时，使用 `portable-signed-audit`；宿主从真实工具响应签发短时效 `qa/live-current-root-receipt.json`，仓库只验签不签发：

```bash
python3 -I -S scripts/secure_runner.py scripts/validate_transport_fidelity.py handoff.json \
  --intended-html output/new-account-id/article-slug/wechat.html \
  --live-root-export qa/live-current-root.json \
  --live-root-receipt qa/live-current-root-receipt.json \
  --require-live-root
python3 -I -S scripts/secure_runner.py scripts/compile_wechat.py \
  --transport-fidelity handoff.json \
  --live-root-export qa/live-current-root.json \
  --live-root-receipt qa/live-current-root-receipt.json \
  --output output/new-account-id/article-slug \
  --check
```

`article.json` 模板适配器只能显式作为调试预览，它不产生可投递 `wechat.html`：

```bash
python3 -I -S scripts/secure_runner.py scripts/compile_wechat.py article.json \
  --org organizations/new-account-id \
  --authoring-preview \
  --output output/new-account-id/article-slug/authoring
```

输出目录包含：

- `visual-kit-plan.json`：文章专属小组件/小插图生产与验收清单。
- `storyboard-plan.json`：叙事章节、构图和 block 覆盖校验。
- `ardot-manifest.json`：Ardot 开放式构图装配与 QA 清单。
- `visual-review.json`：实际 Ardot 节点的 v3 截图、哈希、尺寸、capture、密度、微组件 inventory 与 node-property 检查证据。
- `index.html`：冻结图层投递预览，不是设计源。
- `wechat-candidate.html` / `candidate-report.json`：`current-session-draft` 的精确结构绑定；可作为本次宿主中的草稿写入输入，但不是 portable/final 证据。
- `wechat.html` / `compile-report.json`：只在 `portable-signed-audit` 中由冻结 Ardot 图层和有效 live receipt 生成的终态内联传输链；chapter y 连续覆盖当前 root，每个可见图层绑定真实 source node、受支持字体/渲染 style 与独立 asset SHA。
- `authoring-preview.html`：从 article JSON 模板生成的非投递调试件，报告 `delivery_eligible: false`，严禁导入公众号。
- 候选/终态报告不可互换：`candidate-report.json` 只表示 current-session 结构通过；`compile-report.json` 记录 host-signed live-root preflight、transport source/revision、postflight和最终 `wechat.html` path/bytes/receipt 绑定。
- `interaction-policy-report.json`（存在动态候选时）：固定 policy、静态回退完整性、保存回读、移动端能力档案与最终 payload 选择。
- `assets/`：本篇文章实际使用的本地图片副本。

投递前将当前 Ardot root 的完整可见文本节点顺序导出为 `ardot-current-root-export`，将其与完整图层 export 写入 handoff v5，再按所选保证档运行对应 gate。下例为 `portable-signed-audit`：

```bash
python3 scripts/validate_workflow_attribution.py handoff.json
python3 -I -S scripts/secure_runner.py scripts/validate_transport_fidelity.py handoff.json \
  --html output/new-account-id/article-slug/wechat.html \
  --live-root-export qa/live-current-root.json \
  --live-root-receipt qa/live-current-root-receipt.json \
  --compile-report output/new-account-id/article-slug/compile-report.json \
  --require-compile-report
```

保存并重新打开草稿后，从实际微信正文提取可见文本（不是源 HTML），并导出逐章 readback。`current-session-draft` 运行：

```bash
python3 scripts/validate_workflow_attribution.py handoff.json \
  --saved-draft-visible-text saved-draft-visible-text.txt \
  --require-readback
python3 -I -S scripts/secure_runner.py scripts/validate_transport_fidelity.py handoff.json \
  --html output/new-account-id/article-slug/wechat-candidate.html \
  --live-root-export qa/live-current-root.json \
  --compile-report output/new-account-id/article-slug/candidate-report.json \
  --require-compile-report \
  --expected-target-account 'exact-account-ref-from-delivery-preflight' \
  --readback saved-draft-readback.json --require-readback --session-draft
```

这次写入、重开与导出必须同时可见于当前宿主轨迹，验证报告必须有 `session_readback_structural_match: true` 和 `portable_audit_verified: false`。`portable-signed-audit` 再跑：

```bash
python3 scripts/validate_workflow_attribution.py handoff.json \
  --saved-draft-visible-text saved-draft-visible-text.txt \
  --require-readback
python3 -I -S scripts/secure_runner.py scripts/validate_transport_fidelity.py handoff.json \
  --html output/new-account-id/article-slug/wechat.html \
  --live-root-export qa/live-current-root.json \
  --live-root-receipt qa/live-current-root-receipt.json \
  --compile-report output/new-account-id/article-slug/compile-report.json \
  --require-compile-report \
  --expected-target-account 'exact-account-ref-from-delivery-preflight' \
  --readback saved-draft-readback.json \
  --readback-receipt saved-draft-readback-receipt.json \
  --require-readback
```

所选模式的全部门禁都必须退出 `0`。内容门禁证明感谢语原生可编辑、可见、非栅格且末位；两档传输门禁都核对每章 section/text/asset、hosted 下载字节、390 px 草稿截图和账号/草稿 ID。只有 portable 档使用宿主 Ed25519 receipt 鉴真完整字节链；current-session 档必须连同当前宿主轨迹一起审查，不得脱离会话声称可携带审计。两档都只能交付草稿；正式发表/群发需另行明确确认。

`--check` 会阻断无效视觉 provenance（source-zero 隔离未确认，或 explicit grammar 缺来源/scope/non-copy/SHA）、未校准/仍为 provisional、底图 family 不完整、缺少分镜、四枚微组件不独立、缺原图下载与派生 lineage、RGB/全不透明伪 RGBA、无真 Alpha、low-Alpha 残留、彩色 halo/碎片/纹理底板、呈矩形透明边卡片、无 Ardot node 证据、缺失或未覆盖全部实际微组件实例、全宽微图、文字框、无左右错落或字号层级不足、缺少或烘焙的表现型字体、缺少默认 2–3 个 semantic interaction modules 或合规静态例外、instance key/hash 不唯一、当前 revision 三态证据不完整、不完整或哈希不符的五类 Ardot 截图，以及任一视觉检查失败的文章。

## 六、投递到公众号

1. 通过目标公众号连接上传正文图片，将本地路径替换为该账号返回的微信图片 URL。SVG `<image>` 只能使用 `mmbiz.qpic.cn` URL。
2. 单独把当前封面上传到目标账号永久素材，取得该账号专属 `media_id`，并在草稿 payload 中设为 `thumb_media_id`。正文图片 URL、SVG 图片和另一账号的素材 ID 均不能代替封面。
3. 若存在动态候选，先运行固定策略校验：

   ```bash
   python3 scripts/wechat_interaction_policy.py candidate.html \
     --fallback fallback.html \
     --output interaction-policy-report.json
   ```

   只允许无 JavaScript、无 ID、元素自身 `begin="click"` 的 `<set>` / `<animateTransform>` 与 CSS 横滑；`details`、跨 ID timing 和无静态等价物直接阻断。
4. 创建或更新一个草稿，然后回读标题、摘要、正文顺序、图片 URL、实际封面、fallback 哈希和 SMIL 结构签名。结构回读成功只代表未被清洗，不代表手机端会执行动画。
5. 动态版只有在目标账号相同、策略版本相同且未过期的 iOS/Android 真机能力档案通过后才可保留；否则更新同一草稿为静态回退并再次回读，不新建重复草稿。
6. 无 API 授权时可退回浏览器导入，但必须保存后重新打开并实际看到封面与正文，不能把“粘贴完成”报告成“已验证草稿”。
7. 正式发布前再次征得明确确认。

组织包中不保存 AppSecret、access token 或其他账号密钥。

## 七、迁移后能否自动生成对应文件资产

可以，但前提是先完成一次组织建模与视觉校准。之后每篇文章都能稳定生成：

- 该公众号对应的 Ardot 原生长文画板；
- 复用或新增的组织组件实例；
- 每篇文章先生图得到的专属微型视觉套件；
- 与路线一致的封面/章节/解释图资产计划；
- `ardot-manifest.json` 装配清单；
- 视觉通过后的微信草稿投递文件。

系统不会假设“所有 AI 组织都长一样”。迁移结果由组织变量模式、路线、组件变体、真实素材和文章类型共同决定。
