# 组织型公众号工作流使用说明

这套工作流用于“换一个组织或公众号，仍能继续生成属于它的文章、视觉素材和微信交付文件”。

## 使用归属

使用本仓库工作流制作的公开推文，在所有正文和自定义 footer 之后必须保留一次可见文本：`感谢拓浙 AI 生态提供本篇内容生产工作流支持。`。它是仓库级使用归属，不是组织品牌文案；Ardot 中保留末位原生可编辑文本，编译、handoff v4 和草稿回读均会校验。

## 一、已有组织包时

查看可用组织：

```bash
python3 scripts/orgs.py list
```

验证组织包：

```bash
python3 scripts/orgs.py validate organizations/<organization-id>
```

查看某类文章适合的视觉路线与组件：

```bash
python3 scripts/orgs.py recommend organizations/<organization-id> recruitment
```

搜索可复用素材：

```bash
python3 scripts/orgs.py search organizations/<organization-id> "招新 校园"
```

## 二、迁移到新公众号

首先为该公众号建立独立组织包：

```bash
python3 scripts/orgs.py init new-account-id \
  --name "新组织或公众号名称" \
  --root organizations
```

将生成：

```text
organizations/new-account-id/
├── organization.json
├── sources.json
├── components.json
├── assets.json
├── ardot.json
└── assets/
    ├── official/
    ├── photos/
    ├── generated/
    └── derived/
```

然后完成组织调研：

1. 收集本轮明确允许的官网说明、原始文案、Logo、活动照片与品牌规范。默认不要打开旧推文布局、旧截图/PDF、旧 Ardot 或其他组织 pack；获准的历史文字只能用于 voice/fact，不能用于视觉校准。只有用户明确要求学习某个风格时，才进入 [style-options.md](style-options.md) 的 `explicit-style-grammar` 分支。
2. 在 `sources.json` 中记录来源和可核验事实。
3. 在 `organization.json` 中确认受众、内容支柱、语气、视觉色彩、视觉母题和文章类型。
4. 默认在 `organization.provenance` 填写 `visual_reference_policy: source-zero`、本轮 `visual_input_source_ids`、四类旧视觉排除项和 `isolation_reviewed_at`。若用户明确选了 style preset，则改用 `explicit-style-grammar` 的来源、scope、review time 与六项 non-copy 契约；后续组织把 preset JSON 登记为来源，不重新打开最初参考。
5. 为每个文章类型提出 2–3 条视觉路线，先在全新 Ardot 页面做 Hero、章节、照片编排、微型插图和信息密度小样，不直接做全文。已审核 preset 只能作为其中一个 route 级选项；未带 `style_grammar` 的 sibling routes 仍是 source-zero。Hero/章节同时对比可编辑表现型标题字，至少批准两个 construction recipe；每个 recipe 至少两种非字体手法与两个可编辑图层，只换字体不算艺术字。AI 底图必须先做一个母版与 1–3 个同系列变体，整个 family 只能选一种 `light`/`dark` surface mode，并登记 family/variant、归一化 copy-safe zone、正文颜色、最低 4.5 对比度和复制区最大 0.10 亮度标准差，不能逐章随机生成。组织包默认启用 `generated_image_watermark.mode: required`；密钥来自仓库外的 `PROVENANCE_WATERMARK_KEY`，必须是以 `hex:` 或 `base64:` 表示的至少 32 个随机字节，不能写进组织包。

```bash
python3 scripts/build_visual_directions.py \
  organizations/new-account-id recruitment \
  --output output/new-account-id/visual-directions.json
```

仓库当前内置的可选 preset 可在 `style-presets/` 查看。`prismatic-paper-editorial` / 绚烂纸本是暖纸、水彩洗染、干刷与颗粒的连续阅读面语法，不是默认配色模板。选择时只把 preset 的 `grammar` 写入被选 route，组织色、字体、照片与组件仍由本组织材料重新校准。`orgs.py validate` 会把 route SHA 与仓库 canonical preset 对照；修改 token 后重新签一个自有 SHA 也不能通过。

6. 用户批准小样后，把 route、background family、typography recipes 与 Ardot 文件/页面/节点回写到 `organization.visual.calibration`。先登记最终 master/companion PNG，再运行下面的验证；它会直接分析像素，阻断明暗跳变、大块黑白、复制区杂乱和文字对比不足。只有通过后才创建文章 root。组织事实与视觉同时确认后，才将状态改为 `confirmed`。`provisional` 组织会被阻断在全文之前。

```bash
python3 scripts/orgs.py validate organizations/new-account-id
```

如果同一组织有多个公众号：

- 语气、受众、视觉与栏目完全一致时，可共用组织包，只更换发布连接。
- 如果是子品牌、校园分会、招新号或不同受众频道，建议建立独立组织包，避免品牌混同。

## 三、为新公众号生成对应资产

先生成资产计划：

```bash
python3 scripts/orgs.py asset-plan \
  organizations/new-account-id recruitment \
  --output output/new-account-id/recruitment-asset-plan.json
```

资产计划会根据该组织的：

- 品牌色与视觉母题；
- 文章类型；
- 当前视觉路线；
- 已有素材库；
- 真实照片与生成图像的边界；

输出每个资产位的状态、建议尺寸、保存目录和生图提示蓝图。

系统可以生成：

- 封面或开场背景；
- 章节主视觉；
- 透明背景点缀插画；
- 流程、系统与技术解释图；
- 照片裁切、压缩和派生版本；
- 与组织视觉路线一致的组件背景资产。

不会生成：

- Logo 或组织标志；
- 报名码、群二维码或公众号二维码；
- 冒充真实人物、活动现场或项目成果的图片；
- 带有生成中文、虚假数据或合作伙伴标志的图像。

将用户提供或已审核的文件放入对应目录。对于不透明的 `generated-illustrative` 底图或纯生成 raster 封面，先保留母版并生成带来源水印的 final derivative；公开报告留在 pack 内，raw watermark ID 的私密记录必须留在 pack 和 Git 之外。先创建私密目录并设定 `PROVENANCE_WATERMARK_PRIVATE_ROOT`；`--private-record` 必须位于该目录下：

```bash
python3 scripts/provenance_watermark.py embed \
  organizations/new-account-id/assets/generated/recruitment-hero-raw.png \
  organizations/new-account-id/assets/derived/recruitment-hero-final.png \
  --key-epoch 1 \
  --report organizations/new-account-id/assets/derived/recruitment-hero-watermark.json \
  --private-record /secure/private-registry/recruitment-hero.json
```

只有报告达到 `local_verified`、`PSNR >= 42 dB` 且完整画面通过 `390px-if-larger → JPEG Q75` 模拟才注册 final 文件：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id visual.recruitment-hero \
  --kind background \
  --title "Recruitment hero background" \
  --location assets/derived/recruitment-hero-final.png \
  --watermark-source assets/generated/recruitment-hero-raw.png \
  --watermark-report assets/derived/recruitment-hero-watermark.json \
  --origin generated-illustrative \
  --style campus-editorial \
  --use recruitment \
  --visual-role illustrative-atmosphere \
  --background-family-id current-family-v1 \
  --background-variant master
```

登记时会用外部密钥重新检测当前像素、独立重跑传输模拟、回算母版/final/公开报告 SHA 与 PSNR，并拒绝源文件覆盖、伪造报告、未知字段、低于视觉门槛的结果或 pack 外路径。成品、公开报告和私密记录都不覆盖已存在路径。真实照片、用户/官方图片、Logo、二维码、透明 `article-micro`、SVG/SMIL 与 QA 截图不修改。V1 不承诺裁切、加边、旋转或透视变换后的截图检出；完整合同见 [provenance-watermark.md](provenance-watermark.md)。

日常查水印用 `detect`（密钥仍由外部 secret manager 注入）：

```bash
audit_dir="$(mktemp -d)"
python3 scripts/provenance_watermark.py detect \
  "/absolute/path/recruitment-hero-final.png" \
  --report "$audit_dir/local-detect.json"
```

退出码 `0` 且报告同时出现 `status: payload_authenticated` / `authenticated: true` 才是通过。本地和微信托管图都要核对 `payload_fingerprint`、`key_epoch`、`version`、`purpose`、`algorithm`；本地图还要求 `input_sha256` 对齐 embed 报告 `post_sha256`。微信端需先下载保存草稿实际返回的 `mmbiz.qpic.cn` 完整图，再运行同一命令；不用截图、裁切图或转码图。退出码 `1` 仅表示 `not_detected`，`2` 表示密钥/输入/路径/格式错误。详见 [provenance-watermark.md](provenance-watermark.md#detection-commands)。

companion 使用相同 family ID，并改为 `--background-variant companion`；在 `organization.visual.calibration.background_family` 同时登记 master、1–3 个 companion，以及：

```json
{
  "surface_mode": "dark",
  "copy_safe_zone": {"x": 0.12, "y": 0.16, "width": 0.76, "height": 0.58},
  "body_text_color": "#FFFFFF",
  "minimum_contrast_ratio": 4.5,
  "maximum_copy_safe_stddev": 0.10
}
```

登记完全部底图后必须再次运行 `python3 scripts/orgs.py validate organizations/new-account-id`。不允许用一张浅色、一张深色拼成 family，也不能在验证失败时进入全文排版。

Logo 或二维码的注册示例：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id brand.logo \
  --kind logo \
  --title "Canonical logo" \
  --location assets/official/logo.png \
  --origin official \
  --style canonical \
  --use all
```

## 四、在 Ardot 生成可编辑文章

根据 `references/article-schema.md` 创建 `article.json`。先写 4–10 个叙事章节，确定每章命题、构图、视觉意图与 block 覆盖：

```bash
python3 scripts/build_storyboard.py article.json \
  --output output/new-account-id/article-slug/storyboard-plan.json
```

分镜批准后先写 `article.interaction_plan`。常规文章使用 `authoring_mode: dynamic-default`，默认 2–3 个 semantic modules：2 个必须分布在实际 early + middle chapters，3 个再增加 late。每个 module 绑定该章 `source_block_indices` 和一个具体读者任务；四个部门分别点击仍只算 1 个 module，但四个 transport instances 要分别登记原文、唯一 fallback key 与 `sha256:<64 hex>`。这套门槛与下面的四类微型视觉套件相互独立，不能用微插图、艺术字或装饰动画凑数。字段与静态例外见 `references/interaction-composition.md`。

只有 `ready_for_visual_kit: true` 才生成文章专属小组件/小插图计划：

```bash
python3 scripts/build_visual_kit.py article.json \
  --org organizations/new-account-id \
  --output output/new-account-id/article-slug/visual-kit-plan.json
```

先按计划生成四枚不同的微型视觉资产。每枚图必须写明 `storyboard_chapter`、正文原句 `source_text`、`concrete_subject`、`action`、`composition_role` 和 `placement`。不再把整篇正文粗暴塞进四个通用生图提示词。

逐张运行真实 Alpha、尺寸与角色宽高比检查：

```bash
python3 scripts/inspect_asset.py path/to/micro.png --role floating-spot
```

先把登记 ID 写入 `article.visual_kit.assets`；此时若尚未有 Ardot component node，计划仍会保持 `ready_for_layout: false`。资产注册示例：

```bash
python3 scripts/orgs.py register-asset organizations/new-account-id \
  --id spot.article-object \
  --kind illustration \
  --title "Article object spot" \
  --location assets/generated/article-object.png \
  --origin generated-illustrative \
  --style article-specific \
  --use recruitment \
  --role floating-spot \
  --generated-for ARTICLE_ID \
  --visual-role article-micro
```

四类角色不能共用图片；四枚图都必须在资产登记中明确绑定当前 `article_id`。旧的通用装饰图不能解锁排版。验图后先在 Ardot 建四个原生 Ornament 组件，再把每个组件的 `file_url`、`node_id`、exact `name` 写回 `article.visual_kit.assets`。此后才把 status 设为 `approved` 并重跑计划。

然后为本篇文章选定 2–4 个 Hero/章节/观点/关键短语/CTA 表现型字体时刻。每个时刻必须引用正文原句和批准的 `recipe_id`，至少实现两种非字体构造手法，并在 `construction` 中写回独立的 Ardot 文本/矢量 node IDs；主文本的 `file_url/node_id/style_id/name` 也必须完整。只换字体会直接失败。完整字段见 `references/expressive-typography.md`。

```bash
python3 scripts/build_ardot_manifest.py article.json \
  --org organizations/new-account-id \
  --output output/new-account-id/article-slug/ardot-manifest.json
```

清单会包含：

- 目标 Ardot 文件、页面、变量集和组织模式；
- 本篇采用的视觉路线与组件变体；
- 每个区块的真实 Ardot 组件名和覆盖内容；
- 需要上传的组织资产及本地路径；
- 视觉 QA 阻断项与微信投递边界。
- 每个区块的开放式构图模式、微型视觉角色与方框比例限制。

如果 `ardot.json` 仍是 `not-linked`，先在 Ardot 中建立或选择组件系统，再填写：

- `design_file.url` 与 `file_id`；
- `variable_mode`；
- `page_names`；
- `component_aliases`。

随后按清单在 Ardot 中：

1. 先把四类小插图做成无默认底色/描边/圆角的原生 Ornament 组件，并确认表现型字体仍是可编辑文本节点。
2. 应用该组织的变量模式。
3. 获取或创建 Hero、章节、观点、步骤/流程、案例和 CTA 组件变体。
4. 建立 390 px 文章根 Frame；所有区块默认开放、无外框。
5. 为每个 interaction module 建一个原生 group component，保留 `closed`、`open`、`fallback` 三态。三态 node、390 px 截图、文件哈希、当前 revision 和组内 instance/hash 覆盖列表全部写回 `interaction_plan`。
6. 用插图切入文字边缘、章节转场、连续路径和 CTA 落点，不能用方框替代视觉节奏。单个微图片层不超过 72% 行宽、整个实例不超过 82%；含字实例不加文字框/底板，主短句至少 22 px 且为局部正文的 1.35 倍。
7. 按叙事章节装配，不按“一个 block = 一个带外框组件”机械堆叠，也不把动态模块相邻堆成组件墙。
8. 从同一 article root 分别导出 Hero、章节、证据、复杂区块和 CTA 五个不同 Ardot 节点的本地 390 px PNG，记录 node、chapter、SHA-256、实际宽高与 capture 时间到 v3 `visual-review.json`。
9. 从同一根导出 `ardot-article-instance-inventory`，列出四类 visual-kit definitions 的全部实际 instance；再为每个 instance 导出 `ardot-node-properties` JSON，包含 instance/image/text/closed-shape bounds、font size、fill/stroke 和 node IDs。逐文件记录 SHA-256，并把 placement 绑定到对应截图 SHA。不要手填宽度比例、偏移或“无框”。
10. 逐项检查主体相关性、风格一致、装饰裁切、尺度变化、照片/插图和谐、泛 AI 装饰、无意义标签、编辑节奏、手机可读性、开放构图、信息密度、底图家族一致性、表现型字体、无烘焙字图、无文字框、无全宽微图、错落构图和微组件字号层级。
11. 为五个截图节点记录与截图哈希绑定的密度样本。默认 `compact-editorial`：正文 15–17 px、行高 1.45–1.62、中文字距 -0.2–0 px、段距 8–14 px、章内主间隔 24–40 px、普通正文区内容占用率 68%–90%、最大无意空洞不超过 20%。
12. 视觉确认后将 Ardot 保留为唯一可编辑源。

详细规则见 `references/ardot-workflow.md`。

## 五、生成微信投递文件

先验证独立截图验收文件：

```bash
python3 scripts/build_visual_review.py visual-review.json --article article.json
```

把路径写入 `article.visual_review_file`。只有验收通过后，才运行隐藏的最终适配器：

```bash
python3 scripts/compile_wechat.py article.json \
  --org organizations/new-account-id \
  --output output/new-account-id/article-slug \
  --check
```

输出目录包含：

- `visual-kit-plan.json`：文章专属小组件/小插图生产与验收清单。
- `storyboard-plan.json`：叙事章节、构图和 block 覆盖校验。
- `ardot-manifest.json`：Ardot 开放式构图装配与 QA 清单。
- `visual-review.json`：实际 Ardot 节点的 v3 截图、哈希、尺寸、capture、密度、微组件 inventory 与 node-property 检查证据。
- `index.html`：内部传输调试预览，不是设计源。
- `wechat.html`：微信内联样式传输片段，不是设计源；静态适配必须保留全部 visual-kit items 为无框、无字图、最大 72% 行宽的 `article-micro` 实例，不能被通用全宽图片渲染器吞掉。
- `compile-report.json`：组织、路线、组件、来源、素材、`interaction_authoring` 两阶段验收与错误报告。
- `interaction-policy-report.json`（存在动态候选时）：固定 policy、静态回退完整性、保存回读、移动端能力档案与最终 payload 选择。
- `assets/`：本篇文章实际使用的本地图片副本。

投递前将当前 Ardot root 的完整可见文本节点顺序导出为 `ardot-current-root-export`，将其相对路径与 SHA-256 写入 handoff v4，再运行：

```bash
python3 scripts/validate_workflow_attribution.py handoff.json
```

保存并重新打开草稿后，从实际微信正文提取可见文本（不是源 HTML），再跑：

```bash
python3 scripts/validate_workflow_attribution.py handoff.json \
  --saved-draft-visible-text saved-draft-visible-text.txt \
  --require-readback
```

两次都必须退出 `0`。第一次从当前 root 证明原生可编辑、可见、非栅格且末位；第二次证明保存草稿中感谢语恰好一次且仍为末位。

`--check` 会阻断无效视觉 provenance（source-zero 隔离未确认，或 explicit grammar 缺来源/scope/non-copy/SHA）、未校准/仍为 provisional、底图 family 不完整、缺少分镜、四枚微组件不独立/无 Alpha/呈矩形透明边卡片/无 Ardot node 证据、缺失或未覆盖全部实际微组件实例、全宽微图、文字框、无左右错落或字号层级不足、缺少或烘焙的表现型字体、缺少默认 2–3 个 semantic interaction modules 或合规静态例外、instance key/hash 不唯一、当前 revision 三态证据不完整、不完整或哈希不符的五类 Ardot 截图，以及任一视觉检查失败的文章。

## 六、投递到公众号

1. 通过目标公众号连接上传正文图片，将本地路径替换为该账号返回的微信图片 URL。SVG `<image>` 只能使用 `mmbiz.qpic.cn` URL。
2. 单独把当前封面上传到目标账号永久素材，取得该账号专属 `media_id`，并在草稿 payload 中设为 `thumb_media_id`。正文图片 URL、SVG 图片和另一账号的素材 ID 均不能代替封面。
3. 若存在动态候选，先运行固定策略校验：

   ```bash
   python3 scripts/wechat_interaction_policy.py candidate.html \
     --fallback fallback.html \
     --output interaction-policy-report.json
   ```

   只允许无 JavaScript、无 ID、元素自身 `begin="click"` 的 `<set>` / `<animateTransform>` 与 CSS 横滑；`details`、跨 ID timing 和无静态等价物直接阻断。
4. 创建或更新一个草稿，然后回读标题、摘要、正文顺序、图片 URL、实际封面、fallback 哈希和 SMIL 结构签名。结构回读成功只代表未被清洗，不代表手机端会执行动画。
5. 动态版只有在目标账号相同、策略版本相同且未过期的 iOS/Android 真机能力档案通过后才可保留；否则更新同一草稿为静态回退并再次回读，不新建重复草稿。
6. 无 API 授权时可退回浏览器导入，但必须保存后重新打开并实际看到封面与正文，不能把“粘贴完成”报告成“已验证草稿”。
7. 正式发布前再次征得明确确认。

组织包中不保存 AppSecret、access token 或其他账号密钥。

## 七、迁移后能否自动生成对应文件资产

可以，但前提是先完成一次组织建模与视觉校准。之后每篇文章都能稳定生成：

- 该公众号对应的 Ardot 原生长文画板；
- 复用或新增的组织组件实例；
- 每篇文章先生图得到的专属微型视觉套件；
- 与路线一致的封面/章节/解释图资产计划；
- `ardot-manifest.json` 装配清单；
- 视觉通过后的微信草稿投递文件。

系统不会假设“所有 AI 组织都长一样”。迁移结果由组织变量模式、路线、组件变体、真实素材和文章类型共同决定。
